Sandbox Lab Ideas

Lab ideas

Each lab below is meant to be done in a sandbox account using a small number of resources. The focus is on understanding traffic flow, access control, connectivity, and troubleshooting rather than building a production-grade architecture.

Recommended order to study

  1. Start with VPC segmentation, firewall, and private access labs to build the core networking foundations.
  2. Move to hybrid connectivity, routing, load balancing, and DNS so you understand traffic behavior across networks.
  3. Practice troubleshooting, NAT, flow logs, and shared VPC patterns to strengthen operational thinking.
  4. Finish with the advanced labs on Cloud Armor, CDN, and NCC to prepare for multi-service and enterprise scale designs.
Networking

1. VPC segmentation and firewall lab

What to do

  1. Create one VPC with at least three regional subnets: app, db, and management.
  2. Deploy a VM in each subnet.
  3. Create firewall rules that allow only specific ports and source ranges.
  4. Test traffic between the VM groups using SSH or ping from allowed and blocked sources.

What it does after implementation

  • Shows how a VPC isolates workloads by segment.
  • Demonstrates how firewall rules control east-west traffic.
  • Helps you learn why default deny and explicit allow patterns matter in exam design questions.
Private access

2. Private Google Access lab

What to do

  1. Create a private subnet without external IP addresses.
  2. Launch a VM in that subnet.
  3. Enable Private Google Access on the subnet.
  4. Test whether the VM can reach Google APIs such as Cloud Storage or BigQuery without a public IP.

What it does after implementation

  • Shows how workloads can communicate with Google services without internet exposure.
  • Reinforces the difference between public access, private access, and NAT.
  • Creates a strong mental model for private-only architectures.
Hybrid

3. HA VPN and Cloud Router lab

What to do

  1. Set up a Cloud Router and connect it to a VPN tunnel.
  2. Configure BGP on both sides using a private ASN.
  3. Advertise a simple on-prem CIDR range to Google Cloud.
  4. Check route propagation and confirm traffic can flow between the networks.

What it does after implementation

  • Creates a working hybrid connection between a cloud network and an on-prem environment.
  • Shows how dynamic routing works with BGP and Cloud Router.
  • Helps you understand which connectivity pattern fits different enterprise scenarios.
Traffic

4. Load balancer failover lab

What to do

  1. Create two backend VMs in different zones or regions.
  2. Deploy an HTTP(S) load balancer in front of them.
  3. Configure health checks and make one backend unhealthy.
  4. Test whether traffic automatically shifts to the healthy instance.

What it does after implementation

  • Validates how traffic is distributed and how health checks affect failover.
  • Showcases the difference between regional and global load balancing patterns.
  • Builds confidence for questions about availability and resilience.
Security

5. Cloud NAT and edge protection lab

What to do

  1. Create a private VM without an external IP.
  2. Configure Cloud NAT so the instance can access the internet for outbound traffic.
  3. Apply firewall rules to allow only required ports.
  4. If available, add a simple Cloud Armor rule or test policy in front of a load balancer.

What it does after implementation

  • Shows how private workloads can still use outbound internet access safely.
  • Introduces the idea of protecting public-facing services before traffic reaches origin workloads.
  • Helps explain why NAT and edge security are different design decisions.
Operations

6. Network troubleshooting lab

What to do

  1. Create a VPC with a few subnets and firewall rules.
  2. Intentionally misconfigure one route or firewall rule.
  3. Use logs, flow logs, and connectivity checks to diagnose the issue.
  4. Fix the path and verify successful communication.

What it does after implementation

  • Teaches a structured troubleshooting process for network problems.
  • Shows how route and firewall mismatch issues can impact connectivity.
  • Develops the practical thinking needed for exam scenario questions.
DNS

7. Split-horizon DNS lab

What to do

  1. Create a private DNS zone for an internal service name.
  2. Create a public DNS zone for the same service name or a public front end.
  3. Configure different answers depending on whether the client is internal or external.
  4. Validate the records from both internal and public clients.

What it does after implementation

  • Demonstrates how internal and external users can resolve the same hostname differently.
  • Explains why split-horizon DNS is useful for enterprise environments.
  • Improves understanding of public/private naming strategies in cloud networking.
Policy

8. Shared VPC and project access lab

What to do

  1. Create a host project with the shared VPC.
  2. Create one or two service projects.
  3. Assign IAM roles so each project can use shared subnets and services.
  4. Test instance connectivity across projects and verify network policy behavior.

What it does after implementation

  • Shows how centralizing network resources can simplify governance.
  • Helps you understand multi-project network design in real organizations.
  • Builds a foundation for learning shared VPC and service networking patterns.
Proxy

9. Squid proxy lab for outbound filtering

What to do

  1. Create a VM instance in a private subnet with no external IP.
  2. Deploy a Squid proxy server on another VM in a different subnet or client network.
  3. Configure the client VM to use the Squid proxy for HTTP and HTTPS traffic.
  4. Use a whitelist or ACL rule to only allow selected domains or destinations.
  5. Test that allowed sites work and restricted sites are blocked.

What it does after implementation

  • Demonstrates how traffic can be centrally inspected and filtered before leaving the network.
  • Shows why proxy services are useful for compliance, content control, and outbound security.
  • Helps you connect real-world proxy design with firewall, routing, and private access concepts.
Resilience

10. Multi-region failover lab

What to do

  1. Deploy the same web app in two regions with separate VMs or backends.
  2. Use a global load balancer and health checks for both regions.
  3. Force one region to fail by stopping or blocking its backend health.
  4. Confirm traffic is redirected to the healthy region and the app stays reachable.

What it does after implementation

  • Shows how multi-region design improves resilience and business continuity.
  • Helps explain global load balancing, health checks, and failover decisions.
  • Builds the exam mindset for choosing the correct design under outage scenarios.
Observability

11. VPC flow logs and traffic analysis lab

What to do

  1. Enable VPC flow logs on one subnet or VPC.
  2. Send traffic between VMs using allowed and denied firewall patterns.
  3. Review the flow log records and identify source, destination, protocol, and action.
  4. Look for dropped packets, blocked connections, or unexpected routes.

What it does after implementation

  • Gives you direct visibility into what traffic is entering and leaving the network.
  • Shows how logs help diagnose access issues and verify firewall effectiveness.
  • Creates a practical foundation for investigations and incident response.
Security

12. Private Service Access and Internal LB lab

What to do

  1. Create a service that must stay private and not be exposed to the public internet.
  2. Configure Private Service Access or an internal-only access pattern.
  3. Place an Internal TCP/UDP Load Balancer in front of the service.
  4. Test connectivity from another internal VM and confirm it is not reachable from the public internet.

What it does after implementation

  • Demonstrates how private services remain internal while still being reachable by trusted workloads.
  • Shows the difference between public exposure and internal-only service design.
  • Helps with exam questions involving private access patterns and internal application delivery.
Cloud NAT

13. Egress-only internet access lab

What to do

  1. Create private VMs without external IP addresses.
  2. Configure Cloud NAT to allow only outbound internet access.
  3. Open only the required outbound destinations or ports.
  4. Confirm that the VMs can reach the internet for updates or external APIs but are not directly exposed.

What it does after implementation

  • Shows a secure pattern for outbound-only internet access from private workloads.
  • Helps you understand NAT in real-world design decisions for private infrastructure.
  • Reinforces why public IP assignment is often unnecessary for private application tiers.
Routing

14. Custom route and next-hop lab

What to do

  1. Set up a VM acting as a NAT or forwarding appliance in a dedicated subnet.
  2. Create a custom route directing a specific CIDR range to the appliance.
  3. Send traffic to that destination and verify the route path.
  4. Compare the result with a default route and explain the difference.

What it does after implementation

  • Builds a strong understanding of custom routing and next-hop behavior.
  • Shows how traffic is redirected when a specific path is needed.
  • Prepares you for route-based exam questions involving traffic engineering and hybrid connectivity.

Advanced labs

These labs are designed for students who already understand the basics and want to practice enterprise-grade traffic management, edge protection, and global connectivity patterns.

Edge Security Difficulty: Advanced

1. Cloud Armor WAF policy lab

What to do

  1. Deploy a public web app behind a global HTTP load balancer.
  2. Configure Cloud Armor with IP allowlists, rate-based rules, and geographic restrictions.
  3. Test a normal request, a blocked request from a denied IP, and a rate-limited burst of traffic.
  4. Review logs and explain which rule matched the request.

What it does after implementation

  • Shows how edge-layer protections reduce bot traffic, abuse, and attack surface before requests reach the origin.
  • Helps you understand how Layer 7 protection differs from firewall and network access controls.
  • Prepares you for architecture decisions involving DDoS protection, abuse filtering, and public app exposure.
CDN Difficulty: Expert

2. Cloud CDN caching and origin failover lab

What to do

  1. Deploy a backend service with static and dynamic content.
  2. Place Cloud CDN in front of the backend and configure cache behavior for cacheable vs. uncached routes.
  3. Test repeated requests for the same asset to confirm caching.
  4. Simulate a backend failure and confirm whether cache or failover logic keeps the service available.

What it does after implementation

  • Shows how CDN improves latency, reduces origin load, and adds resilience for content delivery.
  • Highlights the difference between static caching and dynamic request handling.
  • Builds a strong base for questions related to performance optimization and global user experience.
NCC Difficulty: Advanced

3. NCC hub-and-spoke routing lab

What to do

  1. Create a hub VPC and connect multiple spoke networks using Network Connectivity Center.
  2. Integrate on-prem networks or separate cloud projects into the same connectivity model.
  3. Route traffic between spokes and validate that reachability follows the expected path.
  4. Introduce a route change or a new spoke and observe how connectivity and policy updates propagate.

What it does after implementation

  • Demonstrates how large organizations simplify cross-network connectivity with a centralized design.
  • Helps explain how policy, routing, and interconnectivity are managed in multi-site enterprise environments.
  • Connects classic hub-and-spoke patterns to more modern global enterprise architecture decisions.
Hybrid + Security Difficulty: Expert

4. Global secure access with Cloud Armor, CDN, and hybrid backbone lab

What to do

  1. Place a public-facing app behind a global load balancer with CDN enabled.
  2. Add Cloud Armor policies to restrict user access and block attack patterns.
  3. Connect the origin to a private hybrid network using Cloud Interconnect or HA VPN.
  4. Validate that users reach the app through the edge while backend services remain private.

What it does after implementation

  • Models a realistic enterprise design where performance, security, and private connectivity are combined.
  • Shows why edge protection and private backends are often implemented together in production.
  • Builds the architectural mindset needed for advanced network engineering exam scenarios.
Routing Difficulty: Advanced

5. BGP route filtering and prefix-list lab

What to do

  1. Set up a Cloud Router with a BGP session toward an on-prem or simulated peer.
  2. Advertise several prefixes and then create route filters to allow only selected routes.
  3. Test which prefixes are accepted, rejected, or withdrawn.
  4. Review route propagation and verify the impact on traffic flow.

What it does after implementation

  • Shows how BGP route policy controls what traffic is learned and announced.
  • Helps explain prefix lists, route advertisement control, and route filtering logic.
  • Builds the practical knowledge needed for hybrid connectivity and enterprise routing design questions.
Policy Difficulty: Advanced

6. Policy-based routing and firewall segmentation lab

What to do

  1. Create multiple subnets for different workloads such as app, admin, and shared services.
  2. Apply destination-based routing so some traffic takes a preferred next hop.
  3. Use firewall rules to restrict only the intended traffic between segments.
  4. Validate which traffic follows the custom path and which traffic is denied.

What it does after implementation

  • Demonstrates how routing decisions can be used alongside firewall policy to enforce segmentation.
  • Highlights the difference between control-plane policy and data-plane filtering.
  • Prepares you for exam scenarios involving traffic steering, segmentation, and enforcement design.
Security Difficulty: Expert

7. Advanced firewall policy and east-west filtering lab

What to do

  1. Build an environment with app servers, database tiers, and admin hosts across separate subnets.
  2. Use deny-by-default rules and selective allow rules to control east-west communication.
  3. Add stricter policy for management access, only permitting SSH or monitoring from approved source ranges.
  4. Attempt blocked traffic and confirm the policy prevents it while approved paths still work.

What it does after implementation

  • Shows how layered firewall design creates real security boundaries inside a VPC.
  • Helps differentiate between public exposure, east-west trust boundaries, and privileged access paths.
  • Connects directly to exam questions on least privilege, segmentation, and secure service design.
Routing Difficulty: Expert

8. Route leak prevention and blackhole scenario lab

What to do

  1. Create multiple connected networks with overlapping or conflicting route advertisements.
  2. Introduce an overly broad or unintended route announcement.
  3. Use route filters or policy controls to stop bad propagation.
  4. Observe how traffic is redirected or dropped when a route is removed or blackholed.

What it does after implementation

  • Shows how route leaks can create outages, path confusion, or unintended traffic redirection.
  • Introduces route hygiene and policy enforcement as a core operational skill.
  • Provides a realistic advanced architecture challenge for BGP and hybrid connectivity design.
Traffic Engineering Difficulty: Expert

9. Multi-region traffic engineering and failback lab

What to do

  1. Deploy the same application across two regions with separate backends and health checks.
  2. Configure the preferred path for users from one geography to a primary region and a secondary path for failover.
  3. Simulate a failure or degraded health in the primary region, then trigger failback after recovery.
  4. Monitor traffic behavior, compare latency, and explain why one route is preferred over another.

What it does after implementation

  • Shows how global routing, health checks, and failover policies shape user experience under real conditions.
  • Helps you understand traffic steering for resilience, latency optimization, and disaster recovery.
  • Prepares you for advanced scenarios involving multi-region design, failover, and service continuity.
